# 客户管理域深度解析

> 依据：`api-endpoints.json`（4229 条全量清单）、`probe-results.json`（508 个只读接口实测）、`api-schemas.json`（33 个接口真实捕获 schema）、`reference-data.json`（公海池/数据集实测）、前端 bundle `chunks\chunk-pagesCommon.js`（含服务层模块 599508 等）、`chunks\chunk-i18n.js`（customerPool/tagManagement/baseConfig/approval/flowListDrawer/reFlow 等 i18n 模块）。租户样本：hospitalKey=`bksw9854`，tenantId=`1`，客户总数 `3428`（GET `/v1/channel/getCustomerNumber` 实测）。所有路径均为前端真实调用路径（网关前缀 `https://bksw.hospital.realmerit.com.cn/api`）。

## 一、业务逻辑概述

客户管理域是睿美云的**主数据中枢**，解决"客户是谁、在谁手里、处于什么阶段、值多少钱"四个问题：

1. **建档与档案**：`/v1/customer/add` 建档（支持报备关联 `params:{reportId}`），`/v1/customer/detail` 提供完整档案（基本信息/相关信息/价值信息/其他信息四组表单，对应 i18n `customerDetail.base.detailEdit.key5~8`）。
2. **归属与流转**：客户永远挂在某个"客户池"里（个人池=某员工名下，非个人池=公共），通过转移/转交/申领（需审批）在池间移动，到期未活跃自动回收到公海。这是医美机构"客户资源是公司资产"的核心管控。
3. **分层与触达**：智慧标签（规则自动打标）、RFM 评分、客户价值类型（价值标签）、会员等级构成运营分层；回访计划、企微标签、短信群发挂在客户上做触达。
4. **聚合视图**：客户 360（`/v1/customerOverView/*`）把本域与预约、接诊、咨询、收费、回访、病历、影像等域的数据按 `customerId` 聚合。

与其他域的关系：**预约域**（`/v2/bespeak/bespeakList` 实测可调）、**接诊域**（`/v2/reception/receptionList` 实测可调，`total=17`）、**咨询/面诊域**（`/v1/flowbrandinfo/cardPageByBus`）、**收费域**（`/v1/flowbrandinfo/getCustomerBillingList`，POST+60s 超时）、**回访域**（`/v1/customerOverView/backVisitData`、`/v1/visitPlan/customer`）、**会员域**（`/v1/member/level/getHCustomerMemberLevel`）均以 `customerId`（18 位雪花 ID，实测样例 `511318081658751001`）为外键。`/v1/flowbrandinfo/*` 名义上属"客户流转"，实际一半接口是客户维度的消费/收费聚合查询。

## 三、状态机与业务流程

### 3.1 客户生命周期（来源 → 建档 → 分配 → 跟进 → 到院 → 成交 → 复购 → 沉睡 → 回收）

```
线索/报备池(preparation, 91天)          ← 渠道/来源三级: 客户来源/第二来源/第三来源(channel/*)
   │ POST /v1/customer/add {data, params:{reportId}}          建档即入池
   ▼
个人池(默认 activePeriod=181天) ⇄ 非个人池(公共) ⇄ 黑名单池(black_list_pool)
   │  转移/转交/申领 → /v1/customerApproval/transfer|superTransfer → 审批 approvalAdopt
   │  到期回收：/v1/autoTransfer/addOrUpdate(规则) + transferList(执行记录)
   ▼
跟进(回访计划 visitPlan / 邀约) → 预约(/v2/bespeak) → 到院接待(流水牌 /v1/flowbrand/*)
   │  quickStartAss 接待 → 分诊 turnTo/转到待分诊 → 咨询/面诊 cardPageByBus → 结束 quickEndAss
   │  离店 exit → trueExit(真实离店)；cancelCard 取消叫号
   ▼
成交(收费/划扣) → 客户类型自动判定(成交定义/老客人定义, baseConfig O.key*) → 复购/会员
   │  类型变更需申请: /v1/customerTypeChangeApply/addApply → approval(GET)
   ▼
沉睡/流失: /v1/customerLostDefine/{getConfig,saveConfig,getInitData}
   │  流失定义 = 按 cusType 配 conditions[{condition, day}]（判定方式+天数，i18n C.key141~148）
   ▼
回收回公海 或 进黑名单池；合并/跨店: crossMerge、detail/merge、tenantAlter
```

**客户池到期规则**（i18n `customerPoolDefine`）：新增用户有效期选项 `三个月/六个月/一年/无限期`；到期提醒 `提前1/3/5/7天或不提醒`；有效期上限 9999 天。到期未跟进的客户按规则自动转移（回收），同步下级机构用 `/v1/customerPool/syncDownLevel`。

### 3.2 公海池流转与审批

- 三种操作（`customerPool:customerList.customerOperateExport.key0~5`）：**转移**（转给别人/别的池，需填转移原因，可同步更新回访计划 `formList.key4`）、**转交**（含企微客户转接约束：`formList.key17` "在职成员的每位客户 90 个自然日内仅可被转接 2 次；原跟进成员需近一年登录过企微"）、**申领**（从公海领取到自己，需填申领原因）。
- 审批链路：`POST /v1/customerApproval/approval`(列表, data) → `GET transferInfoById/V2?approvalId=` → `GET approvalProcess?approvalId=` → `POST approvalAdopt`(通过/拒绝, data) → `POST canChangeTargetPool`(校验目标池)；发起侧 `GET transferInitUser`、`GET transferInfo/customerInfo`、`POST transfer`。审批时"不符合转移规则的客户提交申请时自动筛除"（`customerList.index.key17`），可"忽略转移规则"（key22）。
- 转移规则引擎（`/v2/transRule/rule` GET `params:{sourceId,targetId}`；`ruleList?sourceId=`；`POST rule`(建) / `DELETE rule?ruleId=`；`poolTree`；`untied?targetId=` 解绑）：规则块内条件可**标签交集/标签并集**，`满足规则时自动转移`开关、`需要审批`开关、目标池`优先排序`、可绑定"唯一转入客户池"；硬约束：**"非个人池转个人池时不支持自动转移"**（`transferRules.addRules.key17`）。
- 池容量校验：转移导入报 `人数超过目标池上限`（`customerOperateExport.key9`）；建档报 `该客户池的容量已达上限`（`addCustomer.baseInfo.key12`）。

### 3.3 客户类型与流失定义（类型自动判定）

- **成交定义/老客人定义**（i18n `baseConfig:O.*`，客户类型定义页）：按 `消费` 或 `划扣` 两条路径，条件为"客户累计消费金额≥配置金额后 N 天"/"客户购买了项目管理内定义的成交项目"，`满足所有勾选条件`或`满足任意勾选条件`；满足即判定为成交/老客（`O.key23`："可参与判断下次到院即为老客人"）。流失定义判定方式说明：`C.key139`"客户类型为初诊或者复诊的客户"、`C.key140`"客户类型为老客的客户"，`判定方式不能重复`、按`天数`判定。
- **类型变更申请**（`/v1/customerTypeChangeApply`）：`getApplyInit?id=`(初始化) → `addApply`(POST) → `applyList`(GET)/`applyListInit`(POST) → `applyDetails?id=`(PUT 修改) → `approval`(GET 审批)。记录列（i18n `customerTypeChangeRecord.columns`）：`客户/到院次数/定金情况/原客户类型/申请变更类型/变更原因/申请人/申请时间/审批状态`，审批状态枚举 `待审批/审批中/已通过/已拒绝`。

### 3.4 标签体系流程（智慧标签）

智慧标签是"规则引擎+定时任务"（i18n `tagConfig`）：①建标签（分类/颜色/权限组/是否业绩标签/是否审批/生效方式 `下一个月生效还是当时立即生效`/`有效天数`）；②配**激活规则**（`每日定时进行规则判断`，条件支持标签交集/并集，激活人/可见人权限，激活时间段）；③配**失效配置**三选一：`按标签"有效天数"`、`按不满足激活规则`（每天判断不满足即失效）、`按自定义失效规则`；`手动激活的标签也受自动失效配置控制`开关、`失效后不再重复激活`开关。业绩标签需审批（`key39`），且可同步到客户已交费订单消息（`key33`）。皮肤检测标签按"激活后 N 天失效"（0=无限期，`skinDetectionTag`）。

### 3.5 RFM 与客户价值

- 规则侧（`/v1/rfmRule/*`）：`rfmRulePage?isGroup=`(GET)、`editRfmRule`(POST)、`get-rfm-score-type`/`edit-rfm-score-type`、`customerValueTypePage?isGroup=`(GET)、`editCustomerValueType`(POST `{...}`)、`delCustomerValueType`(GET)；`/v2/rfmRule/*`：`rfmRulePage`(POST)、`editRfmRule`(POST)、`switch`(GET 版本切换)、`switch-rfm-rule-type`(POST)、`configPushRecord`(GET `params:{modules:"CHANNEL"|"CHANNEL_WEB"|"DEPT"|"ROLE"}` 推送记录)、`get-channel-rfm-version`/`switch-channel-rfm-version`（渠道 RFM 版本）。
- 结果侧（客户 360）：GET `/v1/customerOverView/getRfmScore?customerId=&isGroup=false` 实测返回 `{"indicator":[{"max":1.5,"text":"距今未消费天数","value":"未到院"},{"max":1.5,"text":"最近一年消费次数","value":"0次"}],"score":"0.00","name":"…","typeName":"null","value":[0,0]}` —— R(最近消费)/F(消费频次)两维打分，`value` 为雷达图坐标，`typeName` 即客户价值类型（价值标签）名。
- `/v1/score/*`（`scoreContentList/scoreContentInfo/replyAdd/scoreContentExport/getRoleList/scoreRoleAddOrUpdate/scoreStatusAddOrUpdate/scoreStatusDelete/synchronizeScore/compute`）为评分内容管理（满意度/服务评分，具体业务口径待验证），`/v1/scoreClear/expireScore` 积分/分数过期清理，`/v1/scoreCostBack/*` 评分冲正配置。

### 3.6 跨店/跨院与关联账户

- **关联账户（家庭户）**：`getCircleAccount/checkCircleAccount/updateCircleAccount/removeCircleAccount/dismissCircleAccount/checkByCircleAccount`；规则（i18n `customerRelationModal.store`）：`同一个电话号码仅允许在一个档案里出现`、设户主、配置`与账户主关系(relationCode)`、`已关联账户存在电话重复档案需先处理`；门店变更会把整户一起带走（`storeChangeModal.key0`）。
- **合并**：院内合并 `PUT /v1/customer/detail/merge {data, params:{theOtherId}}`；跨店合并 `/v1/customer/crossMerge/apply|apply/do|apply/re|check?id=|records`（re=重新发起）；合并前预检走 `/v1/customerMerge/customerRecord|customerBillingRecord|customerDepositRecord|customerEquityCardRecord/customerTreadRecord|customerNotTreadRecord|customerBalanceRechargeRecord`（预约、接待、咨询、面诊、订单、治疗、影像、病历、回访、线索全合并，`合并无法撤销`）。转移前 `POST /v1/customer/checkBeforeChange`。
- **跨院/门店变更**：`/v1/customer/tenantAlter/apply|apply/do|apply/checkForceApproval|apply/getCusInfo|records`、`/v1/customer/tenant/change`、`/v1/customer/tenant/records`、`/v1/customer/crossHospitalCusInfoChange/config`(GET/POST)；到院时若非本院客户需跨院调档审批（`flowListDrawer.thisReceptionContent.key16/20`）。

## 五、Agent 可实现的运营场景

预置客户数据集（GET `/v2/customer/cube/template/get-user-all-cube-config`，实测 74 条）已把高频圈人场景枚举化，Agent 直接按 `systemConfigEnum`+数据集 id 调 `POST /v2/customer/cube` 即可（注意请求体加密）：

1. **成交转化跟进**：`TODAY_NOT_DEAL`(今日未成交)、`DAY_7_NOT_ARRIVAL_AND_DEAL`(最近 7 日到院未成交)、`DAY_30_NOT_ARRIVAL_AND_DEAL`、`DAY_90_NOT_ARRIVAL_AND_DEAL` —— 生成当日"到院未成交"外呼清单。
2. **回访补漏**：`TODAY_ARRIVAL_NOT_VISIT_PLAN`(今日到院无回访计划)、`DAY_3/7_ARRIVAL_NOT_VISIT_PLAN`、`DAY_30_NOT_VISITED`(最近 30 天未回访)、`HALF_YEAR/ONE_YEAR_NOT_VISITED` —— 找出"到院但没人管"的客户，批量创建回访（`/v2/customer/batch/visit`）。
3. **沉睡唤醒**：`HALF_YEAR_NOT_ARRIVAL`、`ONE_YEAR_NOT_ARRIVAL`（未到院）叠加权属池过滤，导出唤醒名单并推送到公海/企微。
4. **消费分层**：`COST_LESS_1000`、`COST_1000_TO_10000`、`COST_10000_TO_50000`、`COST_GREATER_50000` + RFM（`getRfmScore`）→ 高价值客户维护清单；`ARREARAGE`(欠费)、`HAD_DEPOSIT`(有抵扣金) 生成催缴/核销提醒。
5. **会员/老带新运营**：`OLD_NEW_CUSTOMER`、`OLD_NEW_GREATER_2/5_CUSTOMER`、`DAY_7_BIRTHDAY_CUSTOMER`(近 7 天生日)、`BIND_SCRM_CUSTOMER`/`NOT_BIND_SCRM_CUSTOMER`(小程序绑定) —— 生日关怀、转介绍激励、小程序拉新。
6. **公海池健康度巡检**：GET `/v1/customerPool/customerPools` 取 `currentCount` 对比 cpConfig 上限与 `activePeriod`，输出"接近上限/即将到期回收"预警；用 `/v1/autoTransfer/transferList` 核对回收执行记录。
7. **标签圈人**：POST `/v1/smartLabel/listByType` 取全部 276 个智慧标签的 `value` → 按标签交集/并集组装 listEs/cube 条件 → 圈选"业绩标签客户"做专属活动；结合 `tagCount`（企微标签统计）看覆盖缺口。
8. **RFM 分层报告**：`/v1/rfmRule/rfmRulePage` 读规则 → 对目标客户批量调 `getRfmScore`（customerId+isGroup=false）→ 输出 R/F 得分与价值类型分布，联动 `customerValueTypePage` 维护价值标签。
9. **资源归属审计**：`/v1/customerInfoLog/page`（字段级修改日志）+ `/v1/customer/changeRecords` + `/v1/roleManagerInfo/infoByCustomerId`（负责岗位）核对"客户在谁手里/谁改过资料"；跨店变更查 `/v1/customer/tenantAlter/records`。
10. **报备到期监控**：报备池 `activePeriod=91` 天，`/v1/diversion-customer/statistics`（实测 `{total,unAssignCount,todayReceiveCount,repeatCount}`）+ 客户列表 `preDate(报备有效期)` 字段，生成"临期报备"提醒。
11. **360 画像摘要**：组合 `consumeStatistical`(余额/累计消费/欠费) + `arriveDetail`(到店) + `recentAppointment` + `cusRelations`(亲属/朋友网络) 生成客户一句话画像，供咨询师接诊前速览。

## 六、二开注意事项与坑

1. **空值序列化**：大量字段返回字符串 `"null"`/`"[]"`（实测 `detail.base.birthday:"null"`、`customerPoolConfigs` data=`"null"`、`recentAppointment` data=`"null"`）。所有取值必须先判字符串，否则会把 `"null"` 当真值渲染。
2. **分页两套并存**：IPage 系用 `{page,limit}`（返回 `records/total/size/current/pages/countId/searchCount`）；另一系用 `{current,size}`（返回 `total/list`，如 `/v1/scrm/customer/scrmCustomerList`）或 `{index,size}`（前端 tableStore）。**混用直接 20002**。实测：`smartLabel/getList` 用 `{current,size}` 成功（92 页），`customerCase/page` 用 `{page,limit}` 成功。
3. **HTTP 方法不能猜**：探测时大量 20002 报错实为方法不符：`"您不是最新版本，请更新你的系统 Request method 'POST' not supported"`。真实方法以本文第三节/服务层（模块 599508）为准，典型反直觉项：`/v1/label/add`、`/v1/customerSourceConfig/getList`、`/v1/customerfieldconfig/getConfig`、`/v1/rfmRule/get-rfm-score-type`、`/v1/tags/getAllTags`、`/v1/smartLabel/get` 都是 **GET**；`/v1/customer/detail/merge` 是 **PUT**；`/v1/customerPool/batch` 是 **PUT/DELETE**；`/v1/smartLabel/delete`、`/v1/customerApproval/*删除类` 用 **DELETE**。
4. **错误码语义分层**：`20004`="缺少必要请求参数"（`getDetail/getCustomerPhoneNumbers/customerOverView/*` 未带 customerId 时实测）；`20001`=业务校验（`客户为空!`、`客户id不能为空`、`id为空`）；`20002`=参数/方法错误（也用于"数据不存在或已被删除"）；`20004`+`请更新你的系统`=版本未放开（如 `checkByCircleAccount`、`caseLabelType/getList`）。成功码 `10000/10001/10002`，`10002` 表示"成功但数据为空"，`data` 可能是 `"null"`。
5. **加密接口**：`POST /v2/customer/cube`（数据魔方执行）前端带 `__encrypt__:!0` 且 120s 超时（模块 599508）；`checkBigModelFieldValue` 等同族。直调前需逆向加密算法（**待验证**），否则只能用 V1 `/v1/customer/customerCube` 或预置数据集枚举。
6. **隐私与脱敏**：`getCustomerByPhone/listEs` 返回 `137****9799`；`getCustomerPhoneJson` 实测同样脱敏但带归属地。PII 直接落日志有合规风险；手机号全局唯一（"同一个电话号码仅允许在一个档案里出现"），写库前必须 `/v1/customer/check` 查重。
7. **列表规模限制**：客户列表页提示"请使用条件进行过滤，客户数1万以下可用"（`customerList.customerTable.key8`）——全表拉取会被前端限制，批量任务必须带条件分页 + `listEsExport` 走导出通道（60s~10min 超时）。
8. **池容量与规则硬校验**：转入池有人数上限（`人数超过目标池上限`）、容量满禁止建档；转移规则"不符合自动筛除"，`非个人池转个人池不支持自动转移`；企微转接受企微侧频控（90 天 2 次）。绕过审批的直调会被审批流拦截（`checkForceApproval`）。
9. **并发编辑冲突**：档案编辑有乐观锁提示"客户信息与编辑前发生了变更…可能覆盖别人编辑的内容"（`detailEdit.key2`），二开批量写档案必须先 `detail/check`/`checkBeforeChange` 并接受版本冲突。
10. **配置驱动的字段可见性**：`customerfieldconfig`(档案字段配置)、`customerSelectModuleConfig`(客户选择模块)、`sysFieldConfig`、登录态 `k.i.customerDetail_*` 决定字段/按钮显隐；同接口不同租户返回列不一致，二开不要硬编码列清单。
11. **同义双版本并存**：`/v1/flowbrand/*`（旧）与 `/v1/flowbrandinfo/*`（新）并存（`getFlowNum2/cardPage2/setLoca` vs `getFlowNum/cardPage/setLoca`）；`/v1/customer/customerCube`(V1) vs `/v2/customer/cube`(V2 加密)；`/v1/rfmRule` vs `/v2/rfmRule`（含版本切换开关 `switch`）。以新接口为准，旧接口仅做回退。
12. **命名陷阱**：`/v1/customerPool/customerPoolConfigs` 是"业绩分配可选池"（results 域复用）；`customerPickUp` 是**物料取货**不是客户领取；`distribute` 是分账/分润不是客户分配；`diversion-customer` 是分流/线索分配统计；`score` 是评分内容管理，RFM 在 `rfmRule`。
13. **多租户头**：除文档已知的 `Authorization`(裸 JWT)/`lang`/`X-No-Wrap` 外，实测抓包还要求请求头 `tenant: 1`（api-schemas.meta.headers）；部分接口（`/v1/customer/channel/forTenant0`、`tenantAlter/*`）显式操作跨租户数据，需平台级权限。
14. **案例/图片接口路径参数**：`/v1/customerCase/getDetail` 缺参报 20004（带"(缺少必要请求参数)"字样），photos/case 均按 `customerId+caseId` 组合查询，未在 probe 中放行，调用前先用 `getClueList`（✅ 实测）确认项目树维度。
