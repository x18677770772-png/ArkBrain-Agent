# 临床业务流域深度解析（咨询→预约→接诊→治疗→病历→回访）

> 数据来源：`api-endpoints.json`（4229 条）、`probe-results.json`（508 条实测，临床域 130 条、成功 55 条）、`api-schemas.json`（33 条全字段实测）、前端 chunk（`chunk-i18n*.js` 解码枚举 + `chunk-pagesCommon.js` 业务逻辑）。
> 本文所有接口路径、字段名、枚举值均为照抄真实值；凡未经实测验证者均标注「待验证」或注明来源类型。
> 环境事实：API 基址 `https://bksw.hospital.realmerit.com.cn/api`；鉴权 `Authorization: <裸JWT>`（无 Bearer）+ `tenant: 1` + `lang: zh-CN`；响应信封 `{code, msg, data}`，成功码 10000/10001/10002。

## 一、业务逻辑概述（完整就诊链路与各环节职责）

### 1.1 端到端就诊链路（实测接口 + 前端 i18n 佐证）

```
线上线索                到院前                     到院后                                离院后
─────────             ─────────────             ───────────────────────────          ──────────────
网电/面诊咨询          接诊准备(报备/邀约)         接待(reception)→分诊(triage)          治疗记录归档
consultationInfo      preparation*               ↓                                    病历签名/归档
ai-consultation       ↓                          咨询/面诊(consultation)→开单(收费域)    处方发药核销
toConsultation        预约 bespeak/appoint        ↓                                    回访计划执行 visitPlan
↓                     (多疗程/申请审批/排程)       治疗 treatRecord(划扣→核销→结束)        回访规则自动生成
小程序预约(在线面诊)     ↓                          ↓                                    满意度/微信通知
onlinecFaceConsult.    到院 arrivePurpose          病历 medicalRecord→处方 prescription   ↓
                       ↓                          ↓                                    复购邀约 invitation
                       接待签到 ReceptionSignIn    检查 examination/影像 photo/OCR        （回到咨询/预约）
```

### 1.2 各环节职责与核心模块

| 环节 | 模块（接口前缀） | 职责 | 关键事实 |
|---|---|---|---|
| 咨询 | `consultation`、`consultationInfo`、`toConsultation`、`ai-consultation` | 网电/现场/面诊咨询受理，记录主诉/诊断/处理方案/未成交原因，形成线索标签 | 前端枚举 `customerTypeOptions`: `-1空/0初诊/1复诊/2老客人/3其他` |
| 接诊准备 | `preparation*`(39)、`preparationConfig`、`preparationTransferApply` | 报备、预计到院时间、邀约转申请；跨店/跨院转移 | 实测 `GET /v1/preparation/countPreparation` → `{toDay, thisMonth}` |
| 预约 | `bespeak`、`appoint*`、`appointmentApply*`、`appointmentTemplate*`、`bespeakPlan` | 按专家排程预约；单/多疗程；预约申请审批；爽约提醒 | 实测 `POST /v2/bespeak/bespeakList` ✅；枚举 `bespeakStatus` 6 态 |
| 分诊 | `stayTriage`、`triageToUserSetting`、接待内分诊 | 到院接待后把客户分诊给咨询师/医生 | 前端枚举 `waitTriage`: 分诊状态「待分诊/已分诊/作废」 |
| 治疗 | `treatRecord`、`treatPlan`、`treatmentSchedule*`、`cusTreatProgram` | 划扣（扣次数）→治疗执行→核销物料→结束治疗 | 实测 `GET /v1/treatment/getUserByRoleId` ✅；`未到院客户不可划扣`（i18n） |
| 病历 | `medicalRecord*`、`medicalNewFolder`、`medicalStationFolder` | 结构化病历书写→医生/患者签名（eSign/fdd 电子签）→评审→归档 | 前端枚举 `recordStatus`: TEMP_SAVE/NOT_COMPLE/IGNORE/NOT_REVIEW/NO_PASS/PASS/COMPLETED |
| 处方 | `prescription*`、`prescribeConfig` | 开处方→审批→发药/暂不发药→作废；复诊购药 | 前端枚举 `stepType` 0~10 完整处方流转 |
| 检查影像 | `examination*`、`dentalexamination`、`periodontalexamination`、`photo`、`ocr*`、`skinTest`、`threeDModelInfo` | 口腔/正畸检查、拍照对比、报告 OCR 识别指标 | 报告「提交以后无法再修改」（i18n examinationStore） |
| 回访 | `visitPlan*`、`visit`、`invitation`、`summsg`、`wxNotice`、`notice` | 回访计划生成（规则/手动/导入）→执行→反馈；微信模板通知 | 实测 `GET /v1/visitPlan/init` ✅（53KB 全量配置） |
| 手术室/排班 | `operatingRoom`、`schedule`、`shift`、`occupationRecord`、`bedManagement` | 手术间/设备/床位占用、专家排班、班次 | 实测 `GET /v1/schedule/allSchedule` ✅、`getAllScheduleExperts` ✅ |
| 问诊 | `interrogation`、`onlinecFaceConsultation`、`callOrder`、`phoneBox` | 在线视频面诊、云呼叫、录音 | 前端枚举 `facialDiagnosisStatus`: `toBeSeen 待面诊 / interview 已面诊 / applyFailed 申请失败 / toBeConfirmed 待确认` |

### 1.3 与客户/收费域的关系

- **上游（客户域）**：咨询单、预约单、接诊单全部挂在 `customerId` 上；实测客户完整档案 `GET /v1/customer/detail` 中 `related` 节包含 `consultant`（咨询师）、`crossConsultant/crossFlag`（跨院咨询师）、`currentTransInDate`，`base` 节含 `latestArriveDate`。客户 360 明细 `GET /v1/customerOverView/arriveDetail` 与 `recentAppointment` 直接消费接诊/预约数据。
- **下游（收费域）**：治疗记录的「划扣」动作扣减收费域开单项目的次数/有效期（`treatmentDetail` 字段：`oldResidueNum 剩余次数 / oldTotalNum 总次数 / expiryDate 效期至 / deductPerformance 划扣业绩`）；`treatRecord/getBillingItemArrearsFlag`、`getAnaesthesiaOnBespeak` 等接口证明治疗与账单（billingItem）强关联；欠费标记 `noPayPrice 欠费金额` 阻断划扣（「{{treatAlias}}项目存在欠费」i18n）。
- **报表域**：`/report/v1/consultation/allHospitalDayOrMonth`、`/report/v1/wym/timeStatistics/listNewCusReceptionNum`（新客接诊数）、`listOldCusReceptionNum`（老客接诊数）等直接聚合临床域数据（api-endpoints.json，未实测）。
- **成交判定**：消费状态枚举「已成交/未成交」（`customerVisitDetail` i18n）；咨询记录字段 `key1 未成交原因 / key287 未成交原因`，到院明细按「成交/未成交」展示。

## 二、核心实体与数据模型

### 2.1 咨询单（consultation）

**实测字段**（`POST /v1/consultation/getconsultationsum` ✅ code=10001，咨询汇总统计）：

```json
{"firstNum":1,"firstBillNum":0,"firstMoney":0,"firstActualNum":0,"firstActualMoney":0,
 "secondNum":0,"secondBillNum":0,"secondMoney":0,"secondActualNum":0,"secondActualMoney":0,
 "oldNum":0,"oldBillNum":0,"oldMoney":0,"oldActualNum":0,"oldActualMoney":0,
 "totalNum":1,"totalBillNum":0,"totalMoney":0,"totalActualNum":1,"totalActualMoney":0}
```

> 语义：first=初诊、second=二次、old=老客；Num=人数、BillNum=开单人数、Money=金额、ActualMoney=实收（来源：字段名照抄 + `consultTools` 域）。`totalNum=1` 与 `firstNum=1` 联动，说明该客户按初诊计数。

**咨询表单字段**（i18n `consultationCorrect`，即 `consultationInfo/iniConForm` 动态表单）：
`客户姓名 / 开始时间 / 结束时间 / 咨询项目 / 正在服用药物 / 食欲(良好/不良) / 睡眠状态 / 月经是否正常(规律/不规律) / 客人主诉 / 诊断 / 处理方案 / 未成交原因 / 未成交备注 / 服用药物备注 / 诊断内容 / 咨询时长(分钟)`。

**咨询线索客户列表**（`POST /v1/consultationInfo/conCusList` ✅，IPage 信封）：

```json
{"pages":346,"records":[{"age":null,"arrears":0,"birthDay":null,
  "commonLabel":["总消费＜1万","本年消费＜1万","从未消费","从未到院","无赠送",
    "15天以上未回访","1年内有过回访，超1个月未回访","90天未到院"],
  "commonLabelStr":"[\"总消费＜1万\", ...]"}], ...}
```

> `commonLabel` 是系统自动计算的客户标签数组（字符串化 JSON 同时存在 `commonLabelStr`），是「未回访/未到院」类运营场景的现成数据源。

### 3.1 预约状态机（bespeakStatus，前端枚举实测值）

## 五、Agent 可实现的运营场景

> 以下场景全部基于实测接口或实测枚举，可直接编排调用。

1. **今日未成交 / 到院未成交客户跟进**
   数据源：`POST /v1/consultationInfo/conCusSearchEnum`（实测返回 **24 个系统预置人群**，key 为 0~23 序号；探测样本因 320 字符截断仅可见前 16 项）：
   `0 今日未成交客户`、`1 最近7日到院未成交客户`、`2 最近30日到院未成交客户`、`3 最近90日到院未成交客户`、`4 今日到院无回访计划客户`、`5 最近3日到院无回访计划客户`、`6 最近7日到院无回访计划客户`、`7 最近30天未回访客户`、`8 最近半年未回访客户`、`9 最近一年未回访客户`、`10 最近半年未到院客户`、`11 最近一年未到院客户`、`12 消费金额小于1千的客户`、`13 消费金额1千到1万的客户`、`14 消费金额1万到5万的客户`、`15 消费金额5万以上的客户`（16~23 待采样验证）→ 配合 `conCusList`（records 自带 `commonLabel`：「从未消费」「总消费＜1万」等）。链路：枚举选人群 → conCusList 拉人 → 输出跟进清单。

2. **超期未回访清单**
   `conCusList` 的 `commonLabel` 直接含 `15天以上未回访`、`1年内有过回访，超1个月未回访`；枚举人群含 `最近30天/半年/一年未回访客户`。对每条输出：客户名/会员号/最近到院/最近回访 + 计划回访人，可用 `visitPlan/executeBatchVisit` 批量补计划（写操作需用户确认）。

3. **今日到院无回访计划客户**
   枚举人群 `今日到院无回访计划客户`、`最近3日/7日到院无回访计划客户`；或组合：`/v2/reception/receptionList`（今日接待）↔ `visitPlan/planList`（有计划）差集。

4. **治疗未完成客户跟进**
   `POST /v1/cusTreatProgram/getTreatProgramList`（实测 `{current,size}` 分页）取客户治疗项目；`treatmentLists` 字段 `residueNum 剩余数/总数`、`finishFlag 状态`、`noExpireDays 离过期还有X天`、`（已过期）` 标记 → 「疗程剩余≥1 且未过期」= 复购邀约名单；配合回访计划自动建「到期提醒」。

5. **今日/本周预约到院率（爽约分析）**
   `POST /v2/bespeak/bespeakList` 拉当日预约 → 按 `bespeakStatus` 统计（2=已到院、3=未到院=爽约）；爽约明细带 `popUpBailOnFlag`（是否开启爽约提醒）与 `popUpDelayTime`；对爽约客户可发起回访（visitPlan）。

6. **待签名/待归档病历提醒**
   `POST /v1/medicalRecord/getDoctorWaitSignList`（医生待签名）、`getDoctorWaitSignList`（患者侧）、`/v1/medicalNewFolder/getWaitArchiveList`（待归档）；病历列表字段 `undoDoctorSignNum/undoPatientSignNum`（待完成签名数）、`completionDeadline 完成截止时间`、`pigeonholeFlag`。输出「超时未归档」清单。

7. **待分诊积压监控**
   `stayTriage` 域 + `waitTriage` 枚举（待分诊/已分诊）：接待时间距今超阈值的「待分诊」记录 → 推送分诊负责人（`triageToUserSetting` 配置人员）。

8. **回访计划日报**
   `GET /v1/visitPlan/init`（回访人/方式/类型全量枚举）+ `visitPlan/planList`：按 `visitedFlag` 分「待回访/已回访」，按 `userId` 聚合每人今日计划数（对应「当前待回访计划数为 N」，i18n `reportReturnVisitPlan.key1`）。

9. **治疗排程冲突预警**
   `GET /v1/treatmentSchedule/checkTreatmentSchedules` + `operatingRoom/listRoom`：检查手术间/设备/治疗间时间段冲突（i18n 规则：设备与治疗间时间段需一一对应、需连续）。

10. **客服/专属管家任务看板**
    `GET /v2/reception/getManagerConfig`（管家配置）+ `preparation/countPreparation`（今日/本月报备数）+ 回访计划按 `exclusiveServerId` 分组 → 每个专属客服的「报备→到院→成交→回访」漏斗。

## 六、二开注意事项与坑

1. **分页两套并存，混用必炸**：IPage 族（bespeak/reception/treatRecord/medicalRecord/diagnosis/ocr/phoneBox 等）用 `{page, limit}`；`total/list` 族（`visit/list`、`cusTreatProgram/getTreatProgramList`）用 `{current, size}`。传错得 20002「系统开小差了，请重试！」（实测）。同一模块内也有例外（如 visit/list 用 current/size），逐接口核对 probe-results.json 的 `params` 字段。

2. **字符串化空值**：`"null"` / `"[]"` 字符串不是真 null。实测例子：`expertInfos:"[{\"label\":...}]"`（排班）、`commonLabelStr:"[\"总消费＜1万\",...]"`（咨询线索）、visitPlan/init 中 `idList:"[]"`、`maxNumber:"null"`。解析前必须先「字符串化 JSON 反序列化 + 字面 'null' 转 null」归一化。

3. **方法不匹配是常态而非异常**：探测结果中 75 条临床域失败几乎全是 `20002 您不是最新版本，请更新你的系统 Request method 'POST' not supported` —— 意思是**请求方法用错了**（如 `toConsultation/page` 只收 GET，`bespeakPlan/getCustomerInfo` 只收 GET），不是功能下线。`20004 缺少必要请求参数`（如 `cusTreatProgram/getAllTreatPlanByCustomer`）表示路径对但缺 query/body 必填项。`20001` 是业务校验（缺 id/时间/客户id），错误文案直接告诉你缺什么——照文案补参重试即可。

4. **业务码与状态**：成功码 10000/10001/10002 语义不同——10002=「操作成功,数据为空」（records 空但 total 可能非 0，见 5.8 节实测 total=17/2 而 records=[]，**不要只看 records**）；10001=数据非空；10000=操作成功。20000 是租户级未开通（如 `receptionQrCode/getAllConfig` →「当前门店未开通小程序」），此时应降级提示而非重试。

5. **预约写操作的前置校验在文案里**：创建/改期预约需通过：专家排班范围、工作时间、同时间段上限（maxAppointNum/maxNum）、时间重复确认、多疗程不同天、咨询师≠医生。跨院/非共享客户需先「跨院调档审批」。取消多疗程起始预约会级联取消全部疗程，且可退定金（refundFlag）。Agent 自动取消前必须二次确认用户。

6. **治疗/病历/处方是强顺序强校验链**：`未到院客户不可划扣核销`、`划扣前请先完成病历填写`、`欠费项目不可治疗`、核销量超库存需确认、新氧订单划扣后不可逆、资产变更需客户小程序确认。病历编辑/删除被 `fddSignStatus`（法大大电子签）、`pigeonholeFlag`（归档）、`recordStatus`（1=已忽略态禁编辑，待验证数值映射）三重门控——任何自动写病历的流程必须先查这三个字段。

7. **枚举是「租户配置 + 前端字典」双源**：回访反馈（expectedLevel，71=未接听、72=拒绝）、回访方式、回访类型来自 `visitPlan/init` 实测；bespeakStatus/recordStatus/stepType 是前端字典（i18n/源码枚举）。同一语义在列表接口返回「数值」，在详情接口可能返回「中文串」（如 `recordStatusMessage`、`reservationStatu:"已到院"` 直接比较中文字符串）——写判断时优先用数值字段，中文字段仅展示。

8. **treatAlias 变量**：`{{treatAlias}}` 是租户级「治疗」业务别名词（医疗美容/口腔可配置成「护理/正畸」等），i18n 文案里大量出现。二开 UI/通知文案时应原样透传该变量，不要写死「治疗」。

9. **多租户与门店（tenant）**：hospitalKey=bksw9854、tenantId=1（请求头 `tenant: 1`）。集团功能（跨院治疗 crossTreatment、集团下发预约配置 `canEdit=false` 不可编辑）按集团/门店两级下发；`preparationConfig` 的 `channelScopeType`、`treatTenantConfig` 的 `tenants/tenantConfigList` 都是集团-门店配置。回访/预约均有「计划创建门店 vs 实际回访门店」双维度。

10. **微信/短信触达走租户模板**：`wxNotice/list` 实测模板 `{code:"treatPlan",title:"治疗规划",type:2,encoding:"OPENTM208274011",content:"{{first.DATA}}\n患者姓名：{{keyword1.DATA}}..."}`——模板编号（priTmplId/encoding）与占位符由租户在微信公众平台申请，二开自动通知只能选用已有模板，不能自造占位符；`summsg/page` 为短信群发（本租户空）。发送前用 `visitPlan/update-auto-send-flag` 类配置控制自动发送开关（接口清单）。

11. **无人值守调用风险**：全部写接口（add/update/cancel/delete/executeBatchVisit/deductAndVerifyV2/sign/updatePigeonhole 等）在 probe 中未实测（探测仅做只读 GET/分页 POST），其请求体结构仅能从前端调用处推得（待验证）。上线自动化前必须先用单条测试数据人工核验每个写接口的 payload。

12. **敏感数据合规**：患者姓名/手机号/病历/处方属医疗敏感数据（api-schemas.json 采样已做 PII 脱敏：`<MASKED>/<ID>/<EMAIL>/<NUM>`，手机号前3后4）。二开输出的任何报表/消息需同样脱敏；电子签（fdd/fasc/eSign/medicalSign）与知情同意（getDisclaimersRecord）链路涉及法律效力，禁止自动化代签。
